# NX2 Lab: evidence-first strategy (decision proposal, 2026-10-29)

## October 30 competitive reassessment — overrides stale allocation below

The fresh [emulator competition and architecture audit](COMPETITIVE_ARCHITECTURE_AUDIT_2026-10-30.md)
finds active, technically substantial Eden-NS2/Eglantine GPU/runtime forks,
the Apple Silicon native-execution project nxnative, and established
oboromi/Pound/NeXo 2. **Self-reported gameplay is not our verification**.
NX2 has not demonstrated any Nintendo-native process, graphics, frame, or
commercial title. The earlier HBX CPU test is valuable but not enough
to be a leading emulator.

**Updated sequence:** (1) select/qualify a mature separately GPL-compliant
runtime or an upstream contribution path; (2) capture independent
Switch 2-specific ABI and graphics evidence; (3) create a portable
cross-backend conformance suite and first guest-generated frame. Preserve
the MIT lab and pin all sources. Stage-2 HBX input remains a small
source-defined CPU regression, **not the main next milestone**. Do not
begin a new clean-room full CPU/HLE/GPU reimplementation before the
engine selection gate. Maintain an independent authorized security track.

**New NX2 work balance** for this cycle: 40% runtime selection/vertical
integration, 30% platform-specific evidence, 20% reusable conformance
and upstream contributions, 10% controlled vulnerability research.
These replace the 50/30/20 allocation later in this historical document.

## Decision

**Primary mission:** become an independently useful Switch 2 compatibility and
conformance laboratory that feeds an eventual emulator, homebrew ecosystem and
responsible security research. Ship platform-specific *evidence*, not merely
host-only CPU interpreter demonstrations.

**Ultimate emulator goal:** an independently authored, genuine Switch 2-targeted
guest program executes verified CPU, memory and Horizon-facing contracts and
produces a guest-generated visible frame; subsequently support lawful commercial
titles, first with repeatable boot/menus and eventually defined playable routes.
This remains entirely unachieved as of this proposal.

**Independent security goal:** improve platform understanding and find, validate,
and privately report genuine security weaknesses on owned/authorized targets.
No exploit discovery, kernel access, persistent CFW, or payout is guaranteed.
Vulnerability research is NOT a prerequisite for emulator development.

## Evidence hierarchy (never silently promote a lower category)

0. Speculation or social/media demonstration (lead only).
1. Public third-party claim with exact source and date.
2. Independently audited public source, revisions and licence.
3. Independently reproduced **host-only** build or execution trace.
4. Authorized, independently reproduced **physical Switch 2 observation**
   (firmware, source hash, route, repeat count and negative control).
5. Emulator implementation shown to match that physical observation, followed
   by distinct external homebrew / commercial compatibility acceptance.

Current NX2 proves generic AArch64 host-only execution (level 3 for its narrow
fixtures). It has **no** category 4 or 5 Switch 2 ABI/game result.

## Why this pivot

- Existing emulator projects oboromi, Pound/Ballistic and NeXo 2 already work
  on CPUs, memory, IPC, graphics and loaders. NX2's tiny reference interpreter
  is a useful oracle, not a competitive production CPU backend.
- Switch 2 homebrew projects such as HBLauncher have published native ARM64
  source and test harnesses. Their source can inform reproducible **host**
  experiments without implying that NX2 has confirmed any on-device claim.
- Switchbrew documents Switch 2 compatibility-mode hooks in
  nnCompatTrampoline/nnCompatThin/nnCompat; specific candidates include
  core-mask presentation, system tick frequency and graphics API translation.
  These are **research leads**; don't treat a wiki entry as device evidence.
- Published ns2jb research reports tethered userland/system-module execution
  on firmware 23.0.1, not kernel/persistent CFW. Do not cargo-cult its code,
  attempt to bypass licensing, or treat a console demonstration as emulation.

## Second-pass architecture decision (2026-10-29)

The **primary near-term executable target** is source-pinned,
native-facing HBLauncher SDK software—not the Linux echo fixture and
not a commercial game. First reproduce the author's unmodified host/QEMU
AArch64 ABI suite in a separate environment, then bring a frozen original
HBX diagnostic stage into NX2's future guest runner. HBX is the launcher's
**custom** ABI, not proof of Nintendo's native Horizon IPC or console ABI.

Keep **Switch 1 compatibility mode running on Switch 2** as an independent
conformance evidence lane. Its `nnCompat*` overrides, clock and affinity
facts do not establish the native Switch 2 homebrew/game runtime. Preserve
the original Switchbrew public-source confidence level until authorized
physical reference observations exist.

The claim that NX2 will become the "best" cannot be guaranteed. Our
shortest path to external value is reusable cross-emulator correctness
evidence and accepted upstream changes, measured independently of stars,
code volume, or fixture counts. If another emulator already provides the
needed generic CPU/runtime path, test or integrate rather than rewrite it.

First audited native-facing target: [HBLauncher ABI intake](research/hblauncher_host_abi_2026-10-29.md).

## Three coordinated tracks

### Track C — Switch 2 compatibility/conformance (50% of NX2 work)

Produce *small, independent, executable test cases* and clear observed vs
unverified facts. Pick one exact public interface and a source-owned program.
Record required registers, relevant memory effects, service IDs, fault and
return behavior, ordering constraints, and minimal trace format. Prefer an
independent emulator/backend adapter so others can run the same input.

Initial research candidates (do not assert measurements):
1. Compatibility-mode CPU affinity / visible core-mask differences.
2. Tick-frequency and timer conversion differences.
3. One bounded, independently authored HBLauncher CPU/ABI example and its
   host-only tests, clearly separated from actual device behavior.
4. GPU translation boundary only after a published minimal native shader
   test and an independently validated display result become available.

Never extract proprietary Nintendo code or distribute firmware, keys or games.

### Track E — emulator vertical integration (30%)

Keep the existing tiny AArch64 interpreter as a limited *semantic oracle*.
**Stop growing its ISA one instruction at a time** except for an oracle gap
needed to falsify a selected backend. Qualify an existing maintained ARM64
engine (Dynarmic is currently research-only) against a **published conformance
corpus** of exception, memory and SVC pre/post conditions. Backend remains HOLD
until precise fault/rollback, host support, licence/dependency and isolation
questions have written accept/hold/reject evidence.

Next concrete emulator test is an *actual externally authored Nintendo-facing
homebrew workload*, subject to exact revision, licence and test-route review.
Do not count Linux ARM64 echo fixtures or mock syscalls as Nintendo progress.
After a real ABI gate: loader/process entry -> first real service -> first
guest-derived output -> first visible frame. Each stage needs positive and
negative traces and an honest unsupported stop.

### Track S — authorized, responsible security research (20%)

Host-only first: a public-source threat model and input-surface inventory,
structural parsers/IPC serialization test harnesses, boundary-condition fuzzing
with ASan/UBSan and reproducible failure minimization. Do not present defects
in NX2 or test programs as Nintendo vulnerabilities.

Device-specific experiments require: ownership/authorization, explicit
target/version/scope, non-destructive plans, known recovery route, controlled
logs, informed approval for any console change, and a private working area.
Do not lower the security posture of the daily-use Mac to run an unreviewed
USB extension. Never publish a suspected unpatched exploit or sensitive
device data in the public repository.

For an authentic Nintendo vulnerability, follow Nintendo's published
HackerOne scope and coordinated-disclosure procedures, not public issues/PRs.

## First 30 days — decision dates and acceptance criteria

| Decision target | Date | Verifiable acceptance |
| --- | --- | --- |
| C1: public compatibility evidence census | Nov 7 | At least 10 claims each categorized by source, revision, firmware relevance, license, confidence and an explicit *unknown* field; freeze 2-3 first conformance targets. |
| E1: CPU backend decision | Nov 14 | Dynarmic ACCEPT/HOLD/REJECT memo with exact revision, license transitive review, fault/restart negatives, CI host support, and independent trace comparisons. |
| C2: external native-homebrew intake | Nov 20 | One legally reusable native Switch 2-facing source/revision audited, built off-device, and a deterministic host-only first stop documented; hardware results remain unverified unless observed. |
| S1: responsible research harness | Nov 24 | 1 public-source or project-owned parser/serialization target with >=20 documented negative fuzz/regression cases and zero Nintendo-specific exploit claims. |
| C3: independently usable artifact | Nov 30 | Versioned trace/conformance JSON schema, one minimal CLI runner, at least 2 backend adapters or one backend plus a reference oracle, a reproducibility guide, and 1 upstream test/bugfix PR offered for review. |

Dates are **decision/reproducibility checkpoints, not promises of game support
or finding an exploit**. If blocked, publish exact blocker and testable next
hypothesis rather than silently replacing the target.

## Success/failure rules

For **every** PR: which real dependency did it remove, is the source licensed,
what actual program advances, which negative tests fail closed, which claim
category is earned, and who else can reproduce it?

Use one active executable and at most one primary blocker per track.
Weekly review: external reproduce count, distinct verified Switch 2 facts,
upstream accepted contributions, CPU/backend decisions, false-claim corrections,
and **actual** guest execution progress. Zero of these means reassess scope.

**Stop rule (Nov 30):** if no separately usable conformance artifact and no
external developer feedback, shift Track C work into contributions to an
existing emulator/homebrew project rather than creating more NX2-only fixtures.

## Safety, provenance and legal boundaries

Own or be explicitly authorized to test hardware. No commercial firmware,
encrypted game material, keys or exploit-chain details in public CI or source.
Do not imply emulator compatibility from Switch 1 NRO tests, host-side
simulations, mere screenshots or a console exploit. Review dependencies before
vendoring GPL/copyleft work into this MIT repository.
